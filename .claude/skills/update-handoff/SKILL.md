# Update Handoff — 任意时刻增量提炼与 handoff 更新

**目标**：把"下个 agent/session 不知道就会重复工作"的信息提炼出来，写入 handoff.md。handoff 只承载三类信息：关键文件路径、用户偏好、踩坑。
**边界**：本 skill 只更新 handoff.md。context.md 由人主导（用户自行或经 `/tech-note` 更新，agent 不代写）；关键结论、未解决问题、变更概览一律不进 handoff，确认时提示用户经 `/tech-note` 归入 context.md，其中成为"关键文件"的路径才进 Key Files。
**铁律**：先预判价值 → 用户确认 → 才写入；薄/空窗口只小幅更新、不产出候选；就地修正优先（错误结论直接改写旧条目，不并存矛盾小节）；不倾倒、不流水账、不重复已记录内容。
**适用时机**：任意时刻——里程碑达成、用户要求、session 结束；step-by-step 每步完成不自动触发（handoff 频繁更新无意义），由用户主动调用。

## 记忆体系

| 文件 | 角色 | 谁维护 |
|------|------|--------|
| context.md | 结论与决策、过程思路、踩坑、未解决问题的细节主落点 | 用户（自行或经 `/tech-note`；agent 不直接写入） |
| draft.md | 执行计划草稿（临时文件，任务完成后可归档留档） | 用户 + agent（`/gen-plan` 写入初稿） |
| handoff.md | 交接快照：Snapshot + 三类核心信息（≤~80 行） | agent（本 skill，用户确认后写入） |

## Step 0: 增量窗口 + 价值预判（硬门槛，先于一切）

1. **界定窗口**：自上次 handoff 更新以来的增量（step-by-step 场景 = 刚完成的步骤）。
2. **预判**：窗口内是否有 Step 2 三类清单中的条目？只有"不知道就会重复工作"的信息才有价值。
3. **两条路径（二选一）**：
   - **路径 A — 薄/空窗口**（无新踩坑/偏好/关键文件）：不产出候选、不跑 Step 1-5、不弹确认；用户要求更新时只小幅刷新 Snapshot。
   - **路径 B — 有值得记录的信息**：继续 Step 1-5。拿不准时默认走 A。

## Step 1: 回放增量窗口

仅回放本窗口（自上次更新以来）实际发生的事，不是整个 session：用户提了什么要求、改了什么、产出了什么；遇到什么错误/踩坑、怎么解决；用户表达过什么偏好、认可或否定了什么。

## Step 2: 三类筛选清单

逐条归入三类，只保留满足"不知道就会重复工作"标准的条目，每条一句话：

| 类别 | 值得记录的标准 | handoff 小节 |
|------|----------------|--------------|
| 关键文件路径 | 新增/修改的关键文件：路径 + 为什么重要 | Key Files |
| 用户偏好 | 用户明确表达的做事方式、好恶、迭代风格 | 用户要求与习惯 |
| 踩坑 | 环境问题，或一两句话能说清解法、但不知道就要花很久排查的坑 | Do Not Repeat |

**就地修正**：新信息与旧条目矛盾/更新 → 直接改写旧条目（错误原文不留、不做废弃标注、不新增并存小节）；踩坑记录除外——"这样试过会崩"是历史性知识，价值就是"别重复踩"，保留。

**排除标准**（一律不写）：纯叙事/过程细节；完成已批准步骤的实现且无新踩坑/新偏好（"执行"不是"发现"）；用户仅确认/否定已有决策；已在 handoff 记录的内容；git log / git diff 可查的内容；与项目无关的闲聊。

## Step 3: git 兜底核对

```bash
git status --short && git diff --stat
```

核对是否有遗漏的关键文件（agent 记忆可能漏），untracked 的新目录/文件 = 候选 Key Files。

## Step 4: AskUserQuestion 确认（仅候选非空）

候选为空 → 跳过（即路径 A）。筛选结果浓缩为 1-2 个问题，用户的选择就是最终裁决：
- Q1：候选条目（列出简名）是否都进 handoff 对应小节？选项：仅保留满足标准的（推荐）/ 全保留 / 去掉某条 / 补充遗漏——价值存疑的默认剔除，不作候选
- Q2：候选关键文件是否全进 Key Files？（条目 ≤2 时合并进 Q1）
- 候选若属"本该进 context.md 的结论/细节"：一并提示"可由你经 `/tech-note` 整理进 context.md"，由用户裁决，agent 不代写

被用户删掉的条目只留在对话里，不写入任何文件。实现过程中随时浮现的新信息（踩坑/偏好/关键文件）同样须经用户知晓并裁决后才落盘，不能静默写入。

## Step 5: 写入 handoff.md（唯一落盘目标）

**写入规范**（借鉴 keep-it-short 列表规则）：
- 列表仅用于真并列（每条可独立读、自带上下文）；互相依赖（递进/因果/流程）合并为散文
- 压缩时重写为完整白话（保留主谓宾与常用词），禁止电报体动词堆叠（如"空换源"）
- 写入前自问：这条满足"不知道就会重复工作"吗？不满足不写
- 每小节 ≤3-5 句或 ≤3 条真并列点；重复检测 = 遮住任一条，其余仍完整则该条冗余
- 单一正本 + 顺带瘦身：新增前先查同主题旧条目，存在则就地改写/压缩，不并存新小节；每次写入顺手压缩被触及的旧小节

**handoff.md 结构**（Write 整体覆盖，≤ ~80 行）：Snapshot（日期、objective、状态、branch、working tree）；用户要求与习惯；Key Files（表格：路径 / 为什么重要）；Do Not Repeat / Be Careful（只挑关键几条踩坑 + 环境注意）。薄/空窗口只做小幅增量（Snapshot 更新），不整体重写。

## 质量检查（写完后自查）

- [ ] 薄/空窗口走了路径 A：未产出候选、未弹确认、未打扰用户
- [ ] 只写了 handoff.md：未写入 context.md（人主导，结论与细节提示走 /tech-note）
- [ ] 每条都有"不知道就会重复工作"的价值，无流水账、无过程叙述
- [ ] 就地修正：无被证伪结论残留、无并存矛盾小节
- [ ] 列表可独立读，无电报体动词堆叠
- [ ] 旧条目过时的已更新/删除、未过时的保留原样；行数 ≤ ~80
