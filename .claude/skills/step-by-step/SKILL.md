# Step By Step

**铁律：一次只做一步。** 绝不连续执行多个步骤，绝不"顺手"把下一步一起做完。

计划以 Markdown 待办清单（`- [ ]`）记录在项目根目录 `draft.md`（由 /gen-plan 写入、用户可随时改）中，本 skill 负责把计划转成"展示 → 确认 → 执行 → 汇报 →（用户说继续后勾选完成）→ 下一步"的执行循环。

## 核心概念

- **叶级步骤（task plan level）**：没有子步骤的最小可执行单元。**只有叶级步骤会被执行。**
- **一步 = 一个叶级步骤**。
- **嵌套结构**：大步骤可拆成多个小步骤，小步骤还可再拆。所有中间层只是"容器"，只展示不执行。

## 说人话（每步开头和结尾都套用）

- **展示（开头）**：一句话说清"这步做什么、怎么验证"；涉及文件/命令一句；上一步结果一句（有才说）。不展开步骤目的的描述，不重复计划原文。
- **汇报（结尾）**：≤3 句话——做了什么、结果如何、有无问题。不列互相依赖的伪列表。
- 参考 `/keep-it-short` 的规则：先答后述、列表独立可读。

## 执行循环

1. **读取计划**：先读项目记忆三件套——`draft.md`（执行步骤，`/gen-plan` 写入、用户可随时改）、`context.md`（目标与思路）、`handoff.md`（当前状态、Key Files、用户要求与习惯、别踩的坑）。若 draft.md 不存在，与用户确认目标后先在对话中拆分步骤；计划落盘由用户主导——用户自行或经 `/gen-plan` 写入 draft.md，agent 不代写（执行中勾选完成状态除外）。
2. **解析叶级步骤**：将计划展开成有序叶级步骤序列（如 S1.1 → S1.2 → S2.1…），记录每个步骤的编号、路径、状态。
3. **展示当前步骤**（不执行，说人话）：一句话说清这步做什么 + 怎么验证；涉及文件/命令一句；上一步结果一句（有才说）。
4. **请求确认**：用 `AskUserQuestion` 审批当前步：
   - 执行（批准，开始做这一步）
   - 修改步骤（按反馈修改后重新展示）
   - 跳过（标记 skipped，不执行）
   - 停止（终止整个流程）
5. **执行**：仅在批准后执行当前步；遇到计划外情况立即暂停，重新展示。
6. **汇报并确认**（说人话）：≤3 句话说清做了什么、结果如何、有无问题；问一句"还有问题吗"。不得在本步骤完成之前就进入下一个循环。
7. **等待用户信号**：汇报完即停，**不自动展示下一步**。期间用户可自由讨论、追问，agent 只回答、不主动发起确认；用户明确说"继续/下一步"后，**先勾选完成**——把上一步在 draft.md 中对应的 `- [ ]` 改为 `- [x]`（本 skill 对 draft.md 唯一允许的写入：只勾选/标记状态，不改写步骤内容），再回到第 3 步展示并确认。全部叶级步骤完成或用户停止时结束。

## 步骤过大时的拆分

- 若某步骤执行前发现仍然太大（预计需大量子操作或多轮往返），**先暂停**，把它拆成若干子步骤展示给用户确认，再从头走循环（拆解结果如需落盘，由用户经 `/gen-plan` 写入 draft.md，agent 不代写）。
- 拆分后保持叶级步骤 = 最小可执行单元。

## 禁止事项

- ❌ 一次执行多个步骤
- ❌ 批准步骤 A 后顺手把 B、C 也做完
- ❌ 不经过 AskUserQuestion 直接执行
- ❌ 执行中扩大范围；遇到计划外情况不暂停
- ❌ 用户说"继续"时理解为"把剩下的全部做完"——"继续"只代表进入下一步
- ❌ 汇报后没听到用户明确说"继续"就自动展示下一步或发起确认请求；用户讨论、追问时只回答问题
- ❌ 自己重新规划任务或代写 context.md；draft.md 仅允许勾选/标记步骤状态（`- [x]`），不得改写步骤内容或代写新计划（新计划经用户确认后，由用户自行或经 `/gen-plan` 落盘 draft.md，agent 不代写）

## 与其他 skill 的关系

- `/review-no-run`：review-no-run 是"整份计划先展示、批准后再开始"；step-by-step 是"每一步展示-确认-执行"的循环模式。
- `/keep-it-short`：展示与汇报环节直接套用其规则，无需用户另行调用。
