# Ref Planning Files — 只读引用项目记忆（context.md + handoff.md 两文件制）

**目标**：把项目里的 `context.md` + `handoff.md` 当作跨 session 的记忆系统。先从文件中提取与当前问题相关的信息（状态、文件位置、结论、思路、用户要求），再带着这些信息去做真正的查找。
**铁律**：对这两个记忆文件**只读**——绝不写入/更新/删除，不执行任何规划流程、不把本会话进度纳入其中。默认也不主动跑代码（本 skill 的作用是取信息）；但**用户明确要求执行时（运行命令、跑脚本、验证、改文件），直接执行**，不算违反铁律。

## 两文件分工

| 文件 | 角色 | 特点 |
|------|------|------|
| `handoff.md` | **agent 交接快照**：当前状态 snapshot、重要文件位置（Key Files）、下一步、用户要求与习惯 | 短、面向 agent、先读 |
| `context.md` | **人主导的笔记**：详细的开发过程与思路、目标与结论、未解决的问题 | 长、面向"人机对齐"、按需深读 |

- `handoff.md` 的存在是为了给 agent 指路：重要文件在哪、现在是什么状态、用户有什么要求/习惯、下一步做什么。
- `context.md` 由**用户主导**维护：用户把它当笔记，持续理清思路、解决不清楚的问题；agent 不直接写入（仅在用户调用 /tech-note 时协助整理），通过它对齐目标与结论。回答涉及"为什么这样做""怎么想的""结论是什么"时以它为准。

## 读取顺序与提取要点

两个文件都在项目根目录（在 CWD 查找，缺失则跳过，不创建）。

1. **先读 handoff.md**（最快入口，≤~90 行）：回答"现在在哪、下一步是什么、该注意什么"。
   - Snapshot → 当前状态 / 目标 / 进行到哪一步
   - Key Files → 重要文件路径 + 为什么重要（直接拿去查找）
   - 用户要求与习惯 → 回答与执行时遵守
   - Next Best Step / Do Not Repeat / Known Issues → 接下来做什么、别踩什么坑
2. **再按需读 context.md**（详细笔记，可能较长）：需要理解思路、对齐目标与结论时读。
   - 按小节 / grep 关键字定位（"第 N 节"、关键词），不整篇通读
   - 提取：目标与结论、决策思路与取舍、未解决的问题（open questions）、踩坑
   - 与当前问题无关的小节直接跳过

**不要为读而读**：handoff 已概括的不必再读 context.md 全文；context.md 没有的状态细节以 handoff 为准。

## 提取 → 查找的衔接

- 从 handoff 的 Key Files 拿到路径后，直接 Read / Glob / Grep 这些文件；必要时先 `ls` 确认存在。
- 查找范围不限于这两个文件：它们给出**位置线索**，真正的答案在代码/源码里。
- 大规模扇出（多个目录、命名变体）用 Explore agent 代查。
- 引用时标注来源，例如 `handoff Key Files` / `context 第 15 节`。

## 铁律（违反即失效）

1. **禁止写入这两个记忆文件**：不修改 context.md / handoff.md（本 skill 的 allowed-tools 不含 Write/Edit）；如确有需要落盘，提示用户另行安排（agent 在主工作流中更新，或走 /update-handoff），本 skill 不做。
2. **不假设文件存在**：文件可能不存在（新项目）——不存在就跳过，不创建。
3. **不把内容当真相**：handoff 是快照可能过期；context.md 是笔记，可能过时或含未定结论。引用路径前确认存在，引用结论时以当前代码和用户最新意图为准（`git status` 可帮助识别已变更部分）。
4. **不代替用户决定**：提取到互相矛盾的信息（handoff 说 A、context 说 B、代码已改 C）时，呈现差异让用户裁决。
5. **用户明确要求执行时可执行**：只读是默认姿态，不是拒绝执行的借口。用户说"跑一下 / 执行 / 验证 / 按这个改"时直接动手，别拿"本 skill 只读"推脱。

## 完成形态

回答中包含：结论 + 信息来源标注（哪个文件/哪一节）+ 关键文件路径（file:line 可点击）。
